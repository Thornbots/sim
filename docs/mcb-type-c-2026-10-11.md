# Type C board execution, 2026-10-11

Mac mini `blaises-mini`, Jazzy arm64 container. Firmware source is the
`track-i/type-c` startup fix based on MCBV3 `49e5023`; control gains, offsets,
command selection and the Jetson payloads are unchanged. Renode is pinned to
1.17.0; maintained installation, peripheral design and limits belong to
[the Type C backend](../README.md#type-c-board-execution-with-renode).

## Board boot and traffic

An exploratory external-control probe ran the normal ARM release ELF for
11.5 virtual seconds: 3.5 seconds with no DBUS remote, then eight seconds with
stationary motor feedback, DBUS and referee frames. No firmware RAM, PC,
calibration state or controller setpoints were patched.

- The firmware performed its own 4,000-sample calibration.
- The exploratory C callback counted 16,502 command frames for each handle.
  Those counts cannot establish CAN2 traffic: the callback registration omitted
  its bus descriptor, so both handles observed CAN1. Auto-drive produced
  nonzero CAN1 drive words.
- USART1 emitted 13,896 bytes: 384 valid POSE and 42 valid REF_SYS frames,
  with zero CRC8/CRC16 failures.
- Artifact: `/tmp/dexec_83376.log`, UART bytes in
  `/tmp/track-i-renode/run/board.uart`, inside the container.

Renode exposed a real startup problem: assignments of temporary Mersenne
Twister objects in the global gimbal and odometry constructors used roughly
2.5 KiB apiece on the 3 KiB startup stack. Direct initialization removes the
temporary. The generators are used only by system-identification builds;
their standard seed now makes excitation reproducible without unsupported
bare-board entropy. The ARM release constructors reserve 24 and 16 bytes
locally, respectively, instead of those temporary objects.

## CAN and gz motion

The on-demand `mcb_physics_suite` runs a fixed-base gz world, with the board
ELF under Renode driving the same motor plant as the hosted fixture. Its CV
commands enter USART1 through the PTY. Encoder/RPM/current feedback goes
through the STM32 CAN peripheral and firmware ISR/polling path; only actual
board CAN outputs apply forces in gz.

| Target yaw | Measured yaw | Peak shaft speed |
| --- | --- | --- |
| 0.6 rad | 0.60143 rad | 206.571 rad/s |
| −0.5 rad | −0.501499 rad | 420.080 rad/s |

`/tmp/dexec_88359.log` passed the native log checker. The final suite revision
also reads the board UART: `/tmp/dexec_90002.log` passed with 541 POSE and
60 REF_SYS frames and zero CRC failures across the two movement checks.
Its original 0.03 rad position and 0.05 rad/s stopping tolerances were retained.
Renode and gz exited cleanly, and the PTY link was removed. The final run took
283.152 wall seconds including board boot and six scored sim seconds.

Earlier attempts were rejected: a client/server startup race aborted the
adapter; a wrong-cased NVIC property prevented server creation; and an
incorrect pitching-IMU model plus wall-time CV flooding produced a 0.082 rad
error and failed the reverse movement. Startup now waits for the listener,
the NVIC property enables divide-by-zero trap writes, the sentry sensor model
uses yaw-only mounting, CV traffic follows sim time, and UART transfers cannot
cross another device's host-control window. These failed runs are not evidence
of valid motion.

## Checks and boundaries

### Review and corrections, 2026-10-12

The stopped continuation left no new sim/firmware commits. Its uncommitted
adapter moves periodic motor feedback and 14 ms DBUS repetition into Renode's
virtual clock, captures each physical CAN bus in its own device, and reconnects
the external-control session before the pinned server's receive stack grows
without bound. None of these changes write firmware RAM or control setpoints.

The former Renode pitch value of 24,000 was CAN1's odometry-motor command,
misidentified as CAN2 pitch. The pinned C client's
`renode_register_can_callback` omits `can->id` from its request header.
The new per-bus device path avoids that callback. A stationary probe using
the normal board ELF (`/tmp/dexec_93334.log`) reported pitch −10,000 and
head pitch −0.000139475 rad, matching the hosted stationary probe. The
board completed calibration with 16,004 captured command frames and shut
down cleanly. The existing motion bench now checks nonzero pitch output
against the sentry firmware's 10 V clamp.

The continuation's `/tmp/dexec_32354.log` passed the yaw/UART bench (541
POSE, 60 REF_SYS, zero CRC errors). Its parked run `/tmp/dexec_33566.log`
reached scoring but exceeded the harness's wall-time budget during settling;
it did not pass. The Renode scoring budget now accommodates slow instruction
execution while retaining the clock-stall and lockstep-timeout guards.

The bridge drops queued frames whose estimated send start precedes sim clock
zero. Its signed timestamp calculation and UART payloads are otherwise
unchanged. Current firmware differences are limited to constructing the sysid
generators in place; no normal gains, offsets or odometry frame changes were
added. The parallel raw-aim/navigation work remains separate.

The first renewed parked run (`/tmp/dexec_96008.log`) produced 16 physical
indexer exits before failing at a control-session reconnect around sim 12.2 s.
The pinned client attempts to receive from a closed descriptor when no server
is yet listening; the adapter now waits for LISTEN before reconnecting. The
run is invalid (clock-stall rejection and two lockstep timeouts), and its
Gazebo abort is a consequence of the adapter exit, not the unrelated bridge
shutdown issue. The new standalone connection suite (`/tmp/dexec_1874.log`)
passed 24,000 requests across two reconnects in 2.358 wall seconds, preserving
the motor device's feedback bytes and cleaning up its Renode process.

## CAN receive-path correction (2026-10-12)

A read-only board probe supplied wheel feedback for 1 m/s but all four firmware
shaft RPM values remained zero. The model generated 60 frames per 10 ms; the
CAN1 filter-enable register was `0x4000` instead of `0x4001` after CAN2 initialized.
Renode 1.17.0's CAN2 software-reset handler clears shared filters. `TypeCCan`
uses the model's existing slave-aware reset instead. The reset/reconnect
regression fails without the correction (expected filter mask 1, actual 0)
and passes with it, including 24,000 requests across two reconnections (2.482 s).
Prior command-frame and parked-shot checks did not establish CAN1 feedback
reception; closed-loop driving must be revalidated after this correction.
